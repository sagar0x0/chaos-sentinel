# Chaos Sentinel: Incident Response Runbook

This runbook provides actionable steps for SREs and on-call engineers responding to alerts generated by the Chaos Sentinel Prometheus/AlertManager stack or the ML Decision Engine.

## 1. Initial Triage & Verification

When an alert fires in the `#alerts-critical` Slack channel:

1.  **Acknowledge the Alert:** Click the "Acknowledge" button in Slack to let the team know you are investigating.
2.  **Verify in Grafana:** Click the dashboard link in the alert. Check the "Live Risk Telemetry" chart.
3.  **Check Sentinel UI:** Open the React dashboard (`http://localhost:3000`) to view the real-time node map and active ML risk scores.
4.  **Confirm Auto-Healing:** Check the "Decision Engine Audit Log" in the UI to see if the Sentinel actuator has already triggered a pre-emptive recovery action.

## 2. Specific Alert Procedures

### HighCPUUsage (CPU Spike)
*   **Trigger:** Pod CPU > 80% for 2m.
*   **Diagnosis:**
    *   Check `container_cpu_usage_seconds_total` in Prometheus.
    *   Check if `StressChaos` experiments are active: `kubectl get stresschaos -A`.
    *   Check ingress traffic metrics to rule out a DDoS flood (`scenario4_ddos.yaml`).
*   **Resolution:**
    *   If a chaos experiment is rogue, delete it: `kubectl delete stresschaos --all`.
    *   If legitimate load, scale the deployment: `kubectl scale deployment <name> --replicas=3`.

### MemoryBloat
*   **Trigger:** Memory working set > 850MB.
*   **Diagnosis:**
    *   Check if `redis-cart` is accumulating keys without TTL.
    *   Look for OOMKilled events: `kubectl describe pod <pod-name> | grep -i oom`.
*   **Resolution:**
    *   The Decision Engine *should* auto-restart `redis-cart` and reapply limits. If it failed, manually restart: `kubectl delete pod -l app=redis-cart`.

### High5xxErrorRate
*   **Trigger:** > 0.5 5xx errors/sec.
*   **Diagnosis:**
    *   View application logs: `kubectl logs -l app=<service> --tail=100 | grep "500"`.
    *   Check downstream dependencies using the Sentinel Node Map (e.g., if `checkoutservice` is throwing 500s, is `payment` or `shipping` down?).
*   **Resolution:**
    *   Rollback deployment if a bad image was pushed.
    *   If a pod is quarantined via NetworkPolicy (`scenario5_pod.yaml`), remove the label: `kubectl label pod <pod> app- security-status-`.

### SLOBreach (Fast Burn)
*   **Trigger:** Error budget burn rate > 14.4x for 1h.
*   **Action:** This is an all-hands-on-deck incident. A severe degradation is occurring that will wipe out the monthly error budget in under 3 days. Declare an incident in incident management tooling and assemble a war room.

## 3. Threshold Tuning Guide

Alert thresholds may need tuning as baselines evolve.

1.  **Analyze Historical Data:** Query the metric in Grafana over a 7-day period to establish the normal baseline (P95 and P99).
2.  **Calculate False Positives:** Adjust the threshold so it only triggers on the top 1% of anomalies.
3.  **Adjust `alert_rules.yaml`:** Modify the `expr` or `for` duration.
    *   *Increase `for` duration* (e.g., 2m to 5m) to ignore transient spikes.
    *   *Increase threshold value* to accommodate expected higher load.
4.  **Update ML Models:** The Sentinel `IsolationForest` auto-tunes on startup. To retrain, restart the predictor pod to capture the new baseline.

## 4. Escalation Matrix

1.  **L1 (Automated):** Sentinel Decision Engine attempts autonomous remediation.
2.  **L2 (Primary On-Call):** Investigates within 15 mins if L1 fails or alert persists.
3.  **L3 (Service Owner):** Escalate to specific application developers if the issue is code-related (e.g., unhandled exception causing crash loops).
